# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

This is an **infrastructure load-testing project**, not a production trading system. The end goal: collect real historical market data from Upbit, feed it to a "trader" application that replays it as massive simulated trading traffic against an order-acceptance API + matching engine, and use that traffic to load-test the backend + infra. Six independent Go modules live in this repo so far: `backend/` (market data collection + serving), `trader/` (data-replay + bot engine, produces FR-17 order-record files), `orderapi/` (order acceptance, role "A" — see below), `matching/` (order matching engine, role "B" — Phase 1/single-instance, see below), `replayengine/` (FR-18/19 replay engine — replays `trader`'s recorded order files with no judgment logic, see below), and `frontend/` (a separate Vue/Vite app, see its own `frontend/README.md`, not yet wired to anything backend-side).

Per `requirements.md` 1.2.4, **role A (order acceptance) and role B (matching engine) are architecturally separate applications that only ever communicate via Kafka** (A publishes to the `orders` topic, B consumes it and publishes to `executions`) — never direct calls. `orderapi/` is role A, `matching/` is role B; neither imports the other, and both re-declare their own copies of small shared tables (20-market list, tick-size tiers) rather than sharing Go types across module boundaries.

`backend/` is the service that collects cryptocurrency market data from the Upbit exchange (REST + websocket APIs). Kafka wiring for this data was considered (a `backend/kafka/producer.go` wrapper existed early on) but **decided against and since removed** — see "Data flow" below for why. `backend/go.mod` no longer depends on `segmentio/kafka-go` as a result.

`.env`/`godotenv`-based config loading (`backend/config`) is active — `config.Load()` is called from `main.go` and reads `APP_ENV`, `S3_BUCKET`, `PORT`.

## Commands

`backend/`, `trader/`, `orderapi/`, `matching/`, and `replayengine/` are **separate Go modules** (each has its own `go.mod`), so `cd` into whichever one you're working on before running Go commands; there is no shared workspace file tying them together.

```
cd backend
go build ./...        # build everything
go run .               # starts the HTTP server (see backend/main.go); POST /v1/collect triggers a collection
go vet ./...
go test ./...
go mod tidy
```

```
cd trader
go build ./...
go run . -date=2026-07-27 -speed=60   # replays one day, submitting orders to orderapi (BACKEND_URL/ORDERAPI_URL env vars, see below)
go test ./...
```
Env vars (`.env` locally via `godotenv`, gitignored): `BACKEND_URL`, `ORDERAPI_URL` — both **required, no default** (`log.Fatal` if missing; see Conventions below for why).

### Tests

All five modules have `_test.go` files now (table-driven, stdlib `testing` only — no external test/mock libraries). Convention: tests live beside the code they cover, same package (white-box, so unexported helpers like `order.tickTier` are reachable), `TestXxx` names, `t.Run` subtests for table cases. `go test` (and everything else that isn't `go build`/`go run`) automatically excludes `_test.go` files from the compiled binary — that's a Go toolchain guarantee based on the filename suffix, not something this project configures.

What's covered and why: pure/deterministic logic that's easy to get subtly wrong — `order.RoundToTick` (tick-size table + rounding), `bot.MarketState`'s circular buffer (wraparound indexing), `MarketMakerBot.Decide`, `dataset.BuildBatch`/`BuildStream` (Upbit field → normalized field mapping, event merge+sort), `dataset.localStorage` save/load round-trip, and `backend`'s `manifestHandler`/`fileHandler` (via an in-memory fake `dataset.Storage` in `server_test.go`, and — since `fileHandler`'s `r.PathValue()` only populates when matched through a real `http.ServeMux`, not on a bare handler call — a small mux built in the test with the same route pattern as `main.go`). `orderapi` follows the same handler-test pattern: `server_test.go`'s `fakePublisher` (implements `kafkaclient.Publisher`) stands in for Kafka, so `acceptOrderHandler`/`cancelOrderHandler` are tested (missing key, invalid market, success, idempotent retry doesn't re-publish, publish failure isn't cached so a retry can succeed, cancel-not-found, cancel-then-idempotent-no-op, cancel-already-filled) without a real broker; `validate/validate_test.go`, `idempotency/idempotency_test.go`, `order/order_test.go` cover the pure logic pieces in their own packages the same way `backend`/`trader` do. `matching` follows the same pure-logic-first pattern: `orderbook/orderbook_test.go` covers FR-06's matching scenarios (exact match, partial fill both directions, multi-level crossing, FIFO at one price level, price-gap no-match, cancel, price-string normalization, and a determinism check that replaying the same event log twice yields byte-identical book state — see Architecture below for why that matters) entirely in-memory, no Kafka/Redis; `engine/engine_test.go` covers the Kafka/Redis-facing orchestration (`Apply`, `Recover`, snapshot triggering) against fake `ExecutionPublisher`/`SnapshotStore` implementations, same style as `orderapi`'s `fakePublisher`. `kafkaclient` and `snapshotstore` (the real Kafka/Redis implementations) aren't unit-tested — same rationale as `dataset.s3Storage`/`backend/upbit` below — verified by hand instead (see the end-to-end run described in Architecture). `replayengine` mirrors `trader`'s own test split: `orderstore/local_test.go` is a save/load round-trip against a temp dir (mirrors `backend/dataset/local_storage_test.go`), `submitter_test.go` mirrors `trader/order/http_submitter_test.go` exactly (`httptest.Server`, 202/non-202, fresh-Idempotency-Key-per-call), `replay_test.go` covers `filterRange` (FR-27) and `replayMarket`'s ordering/context-cancellation with a fake `Submitter`.

What's deliberately **not** covered, and why: anything whose real work is a live network/AWS call — `backend/upbit` (real Upbit REST calls), `dataset.s3Storage` (real S3), `collectMarket`/`collectAllMarkets`/`ensureMarketCollected` (wrap `upbit` calls, no injectable fetcher to substitute — would need a refactor to test meaningfully), `client.Fetch*`'s success path against a real backend. These stay verified by hand (spin up `go run .`, hit it with `curl`/`Invoke-RestMethod`/a real `trader` run) the same way they were before tests existed — see the git history in this repo for examples of that workflow (e.g. the concurrent batch+stream request that proved `ensureMarketCollected`'s dedup works). AI bot stubs (`MomentumAIBot`/`MeanReversionAIBot`) aren't tested either — there's no logic yet, just a `nil` return.

### Local Kafka for development

```
cd infra/dev-kafka
docker compose up -d
```

Brings up a single-node KRaft-mode Kafka broker (`apache/kafka:3.7.0`) on `localhost:9092`, auto-creating topics (`KAFKA_AUTO_CREATE_TOPICS_ENABLE=true`). `orderapi/.env` and `matching/.env` hold `KAFKA_BROKER` for connecting to it (gitignored — copy/create locally, they're not committed) — `orderapi` publishes to `orders`, `matching` consumes `orders` and publishes to `executions` (`backend` never used Kafka in practice, and its unused `kafka/producer.go` wrapper has since been deleted — see "Data flow" below).

**`orders` needs exactly 20 partitions (one per market) for FR-11 to work** — auto-creation uses the broker's default partition count (1 on this dev broker), which is wrong for `matching`'s market-rebalancing design (see "Matching engine (role B)" under Architecture below): it needs a true 1-market=1-partition bijection, not "however many partitions auto-create happened to pick." Create it explicitly before starting `orderapi`/`matching` against a fresh broker: `kafka-topics.sh --create --topic orders --partitions 20 --replication-factor 1`. If it already exists with the wrong partition count, delete and recreate it (`--delete` then `--create`) — changing partition count on an existing topic changes what its offsets mean, so this is delete-and-recreate, not resize, and only safe when the existing data is disposable (true for local dev, not for a real deployment, which should just be created at 20 from the start).

**Client-side gotcha**: the broker allowing auto-created topics is not sufficient by itself — `segmentio/kafka-go`'s `kafka.Writer.AllowAutoTopicCreation` defaults to `false`, so a client that doesn't explicitly set it to `true` gets `[3] Unknown Topic Or Partition` against a brand-new topic even though the broker would happily create it. `orderapi/kafkaclient.go` and `matching/kafkaclient/producer.go` both set it explicitly (see Architecture below). Also note topic creation is asynchronous on the broker: the very first publish to a never-seen topic can still fail once even with the flag set — a retry (same or a different request) succeeds; this was actually observed live when `matching`'s `executions` topic was created for the first time (a burst of `Unknown Topic Or Partition` errors while replaying a backlog, self-resolving once the topic finished creating). This is part of why `orderapi`'s idempotency store never caches 5xx responses (see `orderapi/idempotency.go` below): it's what lets that retry actually work.

### Local Redis for development

```
cd infra/dev-redis
docker compose up -d
```

Single-node `redis:7-alpine` on `localhost:6379`, no auth/persistence config — purely a local stand-in for the ElastiCache Redis the design docs call for. `orderapi/.env` and `matching/.env` hold `REDIS_ADDR`. This is the **first real use of Redis anywhere in this codebase** — `matching` writes orderbook snapshots to it (`GET /v1/markets/{market}/orderbook`'s backing store) and `orderapi`'s new orderbook-query handler reads them back. See "Matching engine (role B)" under Architecture for the full design.

**Inspecting messages from Git Bash on Windows**: `docker exec dev-kafka-... /opt/kafka/bin/kafka-console-consumer.sh ...` gets its Linux path mangled by Git Bash's MSYS path conversion (`/opt/kafka/...` becomes a Windows path). Prefix with `MSYS_NO_PATHCONV=1` to stop that.

## Architecture

- **`backend/main.go`** — entrypoint. Starts an HTTP server (`net/http`, stdlib `ServeMux`, no router dependency) on `cfg.Port` (env `PORT`, default `8080`). Routes: `POST /v1/collect`, `GET /v1/markets/data`, `GET /v1/markets/{market}/{kind}`. Does not currently call Kafka.
- **`backend/server.go`** — `collectHandler`: parses `{"date": "YYYY-MM-DD"}` from the request body, computes the UTC `[date 00:00, date+1 00:00)` window, and calls `collectAllMarkets`. Returns 400 on a malformed body/date; otherwise 200 with per-market results (a market-level failure, e.g. requesting a date more than 7 days old, shows up as that market's `status: "error"` rather than failing the whole request). Also `manifestHandler`: validates the `date` query param and returns `batchUrl`/`streamUrl` for all 20 `upbit.TargetMarkets` — purely mechanical URL generation, does **not** touch `dataset.Storage` or check whether the files actually exist (see Data flow below for why that's deliberate). Also `fileHandler` (`{kind}` is `batch` or `stream`): tries `dataset.Storage.LoadBatch`/`LoadStream` first; on `dataset.ErrNotFound` calls `ensureMarketCollected` (see `collector.go`) to collect just that one market on demand, then reads and serves it. 400 on bad `kind`/`date`, 404 on a market outside `upbit.TargetMarkets`, 500 on collection/read failure.
- **`backend/collector.go`** — `collectAllMarkets` loops over `upbit.TargetMarkets`, calling `collectMarket` per market (fetches ticks + every candle granularity from `upbit`, builds batch/stream via `dataset.BuildBatch`/`BuildStream`, saves via the injected `dataset.Storage`). One market's error doesn't stop the others. Also `ensureMarketCollected`: wraps `collectMarket` in a `golang.org/x/sync/singleflight.Group` keyed on `market+start` so concurrent requests for the same market+date (e.g. `fileHandler` serving batch and stream at nearly the same time) collapse into a single `collectMarket` call instead of running it twice.
- **`backend/upbit/candles.go`** — REST client for Upbit's `/v1/candles/*` endpoints. `FetchCandlesInRange` paginates backwards in time (via the `to` cursor) to collect all candles in `[start, end)` for fine-grained units (seconds/minutes); `FetchRecentCandles` fetches the last N candles for coarse units (days/weeks/months) where a single page suffices. Both respect Upbit's ~10 req/sec rate limit with a 110ms sleep between paginated calls.
- **`backend/upbit/ticks.go`** — REST client for `/v1/trades/ticks` (individual trade executions). Also paginates backwards using the `cursor` (last page's `sequential_id`). Upbit only allows querying trade ticks for the last 7 days; `FetchTradeTicksForDate` enforces that and errors otherwise.
- **`backend/upbit/websocket.go`** — legacy real-time ticker client over Upbit's websocket API (`ConnectAndListen`), explicitly marked as legacy in a source comment. Not called from `main.go` currently; streams ticker updates onto a channel for a caller to consume.
- **`trader/`** — separate Go module (`module trader`, own `go.mod`), the data-replay + bot engine described in `docs/market-data-api.md`. Split into role-based sub-packages (import path `trader/<pkg>`) with a layered, cycle-free dependency graph: `client` and `bot` are leaves; `order` depends on `bot` (needs `bot.Decision`); `orderstore` depends on `order` (needs `order.RecordedOrder`); `replay` depends on `client`+`bot`+`order`; `main.go` (package `main`, module root) wires everything together, including `orderstore`. No package is named the same as a variable that holds one of its own values in scope (e.g. `main.go` binds the shared `*http.Client` to `httpClient`, not `client`) — that would shadow the package import within that scope.
  - **`trader/client/`** (`client.go`, `types.go`) — talks to the backend (and, via the same shared client, to `orderapi`). `NewHTTPClient` (5-minute timeout, to tolerate on-demand collection latency on a cache miss — see `backend`'s `ensureMarketCollected`), `FetchManifest`/`FetchBatch`/`FetchStream`. `types.go` re-declares the JSON shapes backend returns (`Manifest`, `BatchFile`, `StreamFile`, ...) rather than importing `backend/dataset` — the two modules are meant to only ever talk over HTTP+JSON, never share Go types at compile time.
    - **`MaxIdleConnsPerHost` bug, found via a real end-to-end run**: `NewHTTPClient`'s `Transport` explicitly sets `MaxIdleConnsPerHost: 100`/`MaxIdleConns: 200` (cloned from `http.DefaultTransport`, whose default is `MaxIdleConnsPerHost: 2`). Discovered by actually running `trader` at `-speed=100` against local `backend`+`orderapi`: with up to 62 goroutines (60 per-market bots + 2 global bots) sharing one client, the default pool size meant connections were constantly closed and reopened instead of reused, which exhausted Windows' outbound ephemeral port range within seconds (`connectex: Only one usage of each socket address`) — every order submission failed *client-side* after the first ~10, never even reaching `orderapi`. Fixed by sizing the idle-connection pool to comfortably cover the max concurrent goroutine count; re-verified afterward (see below) that a real run produces zero connection errors and orders land in Kafka continuously.
  - **`trader/bot/`** (`bot.go`, `marketmaker.go`, `noise.go`, `largeorder.go`, `ai_bot.go`) — judgment logic only (FR-16), no knowledge of HTTP or order wire format. `MarketState` (`bot.go`) is not just a single latest price — a fixed-size circular buffer (`PriceHistorySize`, currently 30) of recent prices behind a `sync.RWMutex`. `Price()` returns the most recent entry (fast path for the per-market algorithmic bots); `History()` returns the buffer oldest→newest (for the AI bots, which need a price *series* to reason about momentum/mean-reversion, not just a point value).
    - **Per-market bots (`Bot` interface)**: **`MarketMakerBot`/`NoiseBot`/`LargeOrderBot`** — plain rule-based algorithms, meant to run as one independent instance *per market* (60 total across 20 markets — see `replay.marketBots()`), each reading that market's own `MarketState`. Per-market is deliberate here: a market maker has to quote against one specific order book, it can't function "portfolio-wide".
    - **Global bots (`GlobalBot` interface, `ai_bot.go`)**: **`MomentumAIBot`/`MeanReversionAIBot`** are **not** per-market — decided deliberately, both for cost (2 Bedrock calls per judgment cycle instead of 40) and because "AI trader scanning the whole board and picking where to act" fits the concept better than 20 independent copies. `GlobalBot.Decide(states map[string]*MarketState) []GlobalDecision` receives *every* market's `MarketState` in one call and can return decisions tagged with whichever markets it wants to act on. Both `Decide` implementations currently always return `nil` — connection points for AWS Bedrock, marked with `TODO` comments, deliberately not implemented yet.
    - All parameter constants (spread %, quantities, fire probabilities, `PriceHistorySize`) are placeholder defaults, not derived from real data — expect to retune them.
  - **`trader/order/`** (`order.go`, `ticksize.go`) — turns a `bot.Decision` into a submittable `Order`. `NewOrder` calls `RoundToTick` (`ticksize.go`) on every price first: bots compute prices as arbitrary floats (e.g. `MarketMakerBot`'s spread math), but `docs/api-specification.md` requires order prices to be a multiple of the market's price-tier-dependent tick size (`INVALID_PRICE_UNIT` otherwise) — without this, essentially every market-maker order would get rejected once a real order API is wired up. `tickTiers` mirrors Upbit's published KRW tick-size table (bigger ticks at higher price bands); `RoundToTick` returns both the snapped price and the decimal-place count for that tier, and `NewOrder` formats with that exact precision (not `strconv.FormatFloat`'s shortest-representation mode) to avoid floating-point noise like `634.00000000001` in the serialized order. `OrderSubmitter` interface decouples "decided to trade" from "how the order actually gets sent" — `main.go` now injects `HTTPOrderSubmitter` (`http_submitter.go`), which `POST`s to `orderapi`'s `/v1/orders` with a fresh `Idempotency-Key` per call (trader has no retry logic, so one `Submit` call is always one new attempt) and returns an error on anything but 202, which is what lets `RecordingSubmitter` correctly skip recording rejected/failed orders. `LogOnlySubmitter` still exists for log-only dry runs (e.g. `orderapi` not running locally) — swap it back in behind the same interface, nothing else changes. `record.go` adds `OrderRecorder`/`InMemoryRecorder`/`RecordingSubmitter` for FR-17 order recording — see the "Order records" subsection under S3 storage design below for the full design (separate S3 bucket, trader writes directly, flush timing).
  - **`trader/replay/`** (`replay.go`, `globalbot.go`) — the orchestration layer, ties `client`+`bot`+`order` together. `ReplayMarket` fetches one market's batch+stream, then walks `stream.Events` in order, sleeping `(events[i].ts - events[i-1].ts) / speed` between events before logging each one and calling `state.Update(price)`; alongside that it runs `marketBots()` as goroutines on a `time.Ticker` at `bot.Interval()/speed`, sharing the market's replay lifetime (`context.WithCancel`, cancelled when the event loop ends). `RunGlobalBots`/`globalBots()` (`globalbot.go`) run the two AI bots the same way but scoped to *all* markets at once — started once from `main.go` (not inside any single market's `ReplayMarket`), sharing the `states` map `main.go` built, stopped only when *all* markets finish replaying. **Known unresolved issue** (marked `TODO` in `globalbot.go`): global bot tickers are scaled by `/speed` like the algorithmic bots, but real Bedrock call latency won't shrink just because replay is sped up — revisit when actually wiring Bedrock (either decouple the AI bots' cadence from `speed`, or skip a tick if the previous call is still in flight).
  - **`trader/main.go`** — `LoadConfig()` (`config.go`, `.env`/`godotenv`, same pattern as `backend`/`orderapi`) supplies `BackendURL`/`OrderAPIURL`; `-date`/`-speed`/`-order-bucket` remain CLI flags (see the Conventions note below on why these two are split). Fetches the manifest, builds a `map[string]*bot.MarketState` (one per market, shared between that market's own replay goroutine and the global bots), then spawns one goroutine per market calling `replay.ReplayMarket`, all sharing a single `*http.Client`. One market's error is logged and collected into a failure summary at the end; it does not stop or cancel the others (plain `sync.WaitGroup` — see `wg.Go` usage throughout `trader/`, Go 1.24+ — deliberately not `errgroup`, whose `WithContext` cancels sibling goroutines on the first error, exactly the propagation this design avoids).
  - **Tick-size rounding (`ticksize.go`)**: bots compute prices as arbitrary floats (e.g. `MarketMakerBot`'s spread math), but `docs/api-specification.md` requires order prices to be a multiple of the market's price-tier-dependent tick size (`INVALID_PRICE_UNIT` otherwise) — without this, essentially every market-maker order would get rejected once a real order API is wired up. `NewOrder` (`order.go`) calls `RoundToTick` on every `Decision.Price` before it becomes an `Order`, so this is handled once centrally rather than per-bot. `tickTiers` mirrors Upbit's published KRW tick-size table (bigger ticks at higher price bands); `RoundToTick` returns both the snapped price and the decimal-place count for that tier, and `NewOrder` formats with that exact precision (not `strconv.FormatFloat`'s shortest-representation mode) to avoid floating-point noise like `634.00000000001` in the serialized order.
- **`orderapi/`** — separate Go module (`module orderapi`, own `go.mod`), the order-acceptance API: role **A** per `requirements.md` 1.2.4. Implements `docs/api-specification.md`'s contract. Architecturally standalone from `matching/` (role **B**) — the two only ever talk via Kafka (`orders` topic in, `executions` topic out), never a direct call; `orderapi` doesn't import anything from `backend`/`trader`/`matching` and re-declares its own copies of small shared tables (20-market list, tick-size tiers) rather than sharing Go types across module boundaries, same rationale as `backend`↔`trader`. Split into role-based sub-packages the same way `trader`/`matching` are (import path `orderapi/<pkg>`): `order`, `validate`, `idempotency`, `kafkaclient` are leaf packages with no dependency on each other except `kafkaclient`→`order` (needs `order.Order` for `Publisher.PublishNew`'s signature); `main.go`/`config.go`/`server.go`/`orderbook.go` (package `main`, module root) wire everything together and hold the HTTP layer. Package names dropped the redundant `Order`/`Idempotency` prefix from their exported types (`order.Store` not `order.OrderStore`, `idempotency.Store` not `idempotency.IdempotencyStore`) — same convention `trader/orderstore.Storage` and `matching/engine.Engine` already established; local variables that used to be named `order` in `server.go` were renamed to `o` to avoid shadowing the `order` package import.
  - **`main.go`** — `LoadConfig()`, `order.NewStore()`, `idempotency.NewStore()`, `kafkaclient.NewOrderProducer(broker, topic)` (deferred `Close()`), a `redis.Client` (`REDIS_ADDR`, deferred `Close()`), registers `POST /v1/orders`, `DELETE /v1/orders/{orderId}`, and `GET /v1/markets/{market}/orderbook` on a stdlib `ServeMux`, `ListenAndServe`.
  - **`config.go`** — `LoadConfig()` reads `.env` via `godotenv` (same pattern as `backend/config`), env vars listed in Commands above.
  - **`order/`** (`order.go`) — `Order` (status one of `ACCEPTED`/`PARTIALLY_FILLED`/`FILLED`/`CANCELED`) and `Store` — an in-memory, mutex-protected map keyed by `orderId`, tracking accepted orders purely so `DELETE` has something to look up/cancel (no persistence; this is not the S3-backed order-*record* store, that's `trader/orderstore` — different concern, different module). `NewOrderID(now)` generates `ord_{YYYYMMDD}_{7-digit seq}` from an atomic in-memory counter.
  - **`validate/`** (`validate.go`) — independently declares `TargetMarkets` (20 markets) and a tick-size tier table, used by `IsTargetMarket`/`ValidateSide`/`ValidatePrice`/`ValidateQuantity` (exported — called from `server.go`/`orderbook.go` in package `main`); the tick-tier table itself and `tickSizeFor`/`isValidTickPrice` stay unexported, package-internal. Deliberately the *opposite* policy from `trader/order/ticksize.go`'s `RoundToTick`: here a price that isn't an exact multiple of its tier's tick size is **rejected** (`INVALID_PRICE_UNIT`), not silently rounded — the API is the enforcement boundary, rounding belongs upstream in whatever generates the order.
  - **`idempotency/`** (`idempotency.go`) — `Store`, an in-memory `map[key]CachedResponse{Status, Body}` (fields exported so `server.go` can read `cached.Status`/`cached.Body` across the package boundary). `Put` does **not** overwrite an existing entry — first response for a given `Idempotency-Key` wins and is replayed verbatim on retry, including for cached 4xx validation failures. Deliberately caches success and deterministic 4xx, but **never** a 5xx (Kafka publish failure) — a transient failure must stay retryable under the same key, which the "auto-topic-creation's first publish can fail once" behavior (see Local Kafka above) depends on.
  - **`kafkaclient/`** (`kafkaclient.go`, `balancer.go`) — `Publisher` interface (`PublishNew`/`PublishCancel`) exists so `server.go`'s handlers can be tested with a fake, without a real broker (`server_test.go`'s `fakePublisher`). `OrderProducer` is the real implementation (`segmentio/kafka-go`), keyed by `market`. Balancer history, two steps: it started as `&kafka.LeastBytes{}` (what the repo's now-deleted `backend/kafka/producer.go` used) — `LeastBytes` ignores the message `Key` entirely and picks partitions by least-accumulated-bytes, breaking the "same market always same partition" guarantee (FR-04/NFR-07), so it was swapped for `&kafka.Hash{}`. That in turn wasn't good enough once FR-11 (market rebalancing, see `matching/` below) needed a true 1-market=1-partition bijection: `Hash` can still collide two markets onto the same partition. `balancer.go`'s `marketPartitioner` replaces it — it looks up the market name's index in `validate.TargetMarkets` (a fixed, ordered 20-market list) and returns that index directly as the partition number, falling back to `&kafka.Hash{}` only for a market outside that list (shouldn't happen in practice, kept as a defensive fallback). This only works because `orderapi`'s and `matching`'s independently-declared `TargetMarkets` lists are byte-identical in ordering (verified via `diff`) — both sides derive the same partition↔market mapping from the same list without ever sharing Go types. Also sets `AllowAutoTopicCreation: true` — see the Local Kafka gotcha above for why. The Kafka message shape (`{"type":"NEW"|"CANCEL","orderId","market","side","price","quantity","acceptedAt","clientRequestId"}`) is **provisional** — `docs/api-specification.md` §6 defers to a separate Kafka message-spec doc (FR-22) that doesn't exist yet; reconcile with that doc once it's written. `clientRequestId` (NEW events only) carries the request's `Idempotency-Key` — added so a future "기록기" can populate `docs/erd.md`'s `TRADE_ORDER.client_request_id` from the `orders` topic; deliberately kept off `order.Order` itself (which doubles as the HTTP response body) so this doesn't change `docs/api-specification.md`'s documented response shape — `Publisher.PublishNew` takes it as a separate parameter instead.
  - **`server.go`** — `acceptOrderHandler` (`POST /v1/orders`): missing `Idempotency-Key` → 400; cached key → replay cached response verbatim (no re-validation, no re-publish); else validates market/side/price/quantity (each failure cached under the key); builds the `order.Order` with `AcceptedAt` in **UTC**, ms-precision (`nowISO()`) — `api-specification.md` §1.2 mandates UTC for this API specifically, an independent decision from the KST choice made for the market-data API/`backend`, since they're different docs/different owners; publishes via `Publisher.PublishNew` (failure → 500, logged, **not cached**, so the client can retry the same key); on success, saves to the `order.Store`, caches the 202 response, returns it. `cancelOrderHandler` (`DELETE /v1/orders/{orderId}`): 404 if unknown; 409 `ORDER_ALREADY_FILLED` if already `FILLED` — **note**: nothing currently sets a stored `Order`'s status to `FILLED`/`PARTIALLY_FILLED` even though `matching/` now exists and processes fills, since `orderapi` doesn't consume `executions` back into its own order store yet (see `matching/`'s "explicitly out of scope" list below) — so this check is currently unreachable in practice, not just "for later"; if already `CANCELED`, returns the previously-stored cancellation result unchanged without re-publishing (idempotent-by-construction, no idempotency-key needed since order state itself already encodes "already canceled"); otherwise marks `CANCELED`, publishes a `CANCEL` event on the same market key (`matching/kafkaclient` consumes this to remove the resting order from its book), returns 200. A `TODO` marks NFR-13 (429 on consumer-lag) as unimplemented — measuring `matching`'s actual consumer lag from `orderapi` isn't wired up yet.
  - **`orderbook.go`** — `orderbookHandler` (`GET /v1/markets/{market}/orderbook`, FR-12, `docs/api-specification.md` §3.1): reads `matching`'s Redis snapshot key (`orderbook:{market}`, written by `matching/snapshotstore`) and aggregates the individual resting orders it contains into price-level `{price, quantity}` pairs, capped at the requested `depth` (default 20, max 100). Independently re-declares the snapshot JSON shape (`orderRestingView`/`orderbookDoc`) rather than importing `matching` — same module-independence rationale as everywhere else in this repo; if that shape changes, both sides need updating by hand. No snapshot yet for a market (Redis `Nil`) → empty book, not an error. Aggregation sums quantities with `shopspring/decimal`, not `float64` — same reasoning as `matching/orderbook` below.
  - Verified end-to-end against the real local broker (`infra/dev-kafka`): correct `key=KRW-BTC`-style partitioning and correct JSON shape for both `NEW` and `CANCEL`, confirmed via `kafka-console-consumer.sh`.

- **`matching/`** — separate Go module (`module matching`, own `go.mod`), the order-matching engine: role **B** per `requirements.md` 1.2.4. Implements FR-05 (orderbook management), FR-06 (price-time-priority matching), FR-07 (partial fills), FR-08 (restart recovery), FR-09's Kafka-publish half (DB storage is a separate not-yet-built "기록기" component per `docs/architecture.md`'s data flow — `matching` is explicitly not responsible for RDS), FR-10 (cancel), FR-11 (market rebalancing across multiple instances, see below), and FR-12 (orderbook query, jointly with `orderapi`'s new handler above). Runs as any number of instances sharing one Kafka consumer group — a single instance still works unmodified (it just gets all 20 partitions assigned to itself).
  - **`orderbook/`** (`orderbook.go`, `match.go`) — pure logic, no Kafka/Redis dependency, fully unit-tested. `OrderBook` holds bid/ask `priceLevel`s (`map[normalizedPrice]*priceLevel`, each a `container/list.List` FIFO queue — **not** a slice, because `Cancel` (FR-10) needs O(1) removal from the middle of a queue, which a slice can't give cheaply) plus a separately-maintained sorted-price-slice per side for O(1) best-price lookup (bids descending, asks ascending — FR-05's own verification bar); `map[orderID]*list.Element` gives O(1) cancel-by-ID. `Apply` (`match.go`) walks the opposite side's best price while it crosses the incoming order, filling FIFO at the **resting** order's price (FR-06) and leaving any unfilled remainder as a new resting order (FR-07); it always re-reads the current best price after a level empties out rather than iterating a stale slice index, so level removal mid-loop can't skip or misread the next level.
    - **Prices/quantities are `github.com/shopspring/decimal`, never `float64`** — at NFR-01/02's target throughput, float summation drift across thousands of fills would risk violating NFR-10's *exact* buy/sell-total-match requirement. Kafka messages carry price/quantity as strings specifically to avoid a float round-trip (same reasoning as `trader/order`'s formatted-precision serialization); `orderbook.normalizePrice` (`.Truncate(8)`, matching the finest Upbit tick tier) is applied before any price is used as a map key, so e.g. `"100"` and `"100.00000000"` land in the same price level instead of silently splitting into two.
    - **Time priority uses the Kafka offset, not a timestamp** — at 10,000 orders/sec (NFR-01), same-millisecond collisions are expected, but offsets are a strict total order within a market's partition. This is also exactly the number `engine`'s recovery checkpoint uses (see below), so it does double duty rather than inventing a second sequence concept.
    - `orderbook_test.go` covers FR-06's matching scenarios table-driven (see Tests above) plus a determinism check: replaying the same event sequence twice must produce byte-identical final book state. This isn't incidental — `engine`'s recovery design (below) is only correct if replay is deterministic, so the test exists to catch anything that would quietly break that assumption (e.g. accidentally keying off map iteration order or wall-clock time).
  - **`engine/`** (`engine.go`) — the per-market orchestration layer sitting on top of `orderbook`, Kafka/Redis-agnostic itself (depends only on its own `ExecutionPublisher`/`SnapshotStore` interfaces, implemented for real by `kafkaclient`/`snapshotstore`). `Apply(ctx, OrderEvent)` applies one `orders`-topic event to the book and publishes any resulting executions (FR-09's Kafka half) or removes a cancelled order (FR-10); **the event's offset is only recorded as "safely processed" after every resulting execution publish has succeeded** — if a publish fails partway through, `Apply` returns an error before advancing that bookkeeping, so a later snapshot can never checkpoint past a fill that was never actually published. `Recover(ctx)` (FR-08) loads the last snapshot for a market (if any) and restores its individual resting orders via `orderbook.Restore` (bypasses matching — these orders already survived their matching decision once, replaying them through `Apply` again would be wrong), returning the offset consumption should resume from.
    - **Recovery is checkpoint-bounded, not "always replay from the beginning"** — this was a deliberate correction from an earlier draft of the design. `docs/requirements.md` 1.2.2's "재시작 시 주문 기록을 리플레이해 복구" literally means replaying the `orders` topic from scratch, but doing that unconditionally means recovery time grows with *total historical topic volume since the topic was created*, not "time since last snapshot" — at NFR-01's target throughput this blows straight through NFR-11's 60-second recovery budget once a test session has been running a while. So `engine` periodically (event-count or wall-clock, whichever comes first — `snapshotEvery`/`snapshotInterval` in `matching/main.go`) snapshots each market's full resting-order list *plus the offset it reflects*, and `Recover` resumes from `snapshot.Offset + 1` instead of offset 0. This still satisfies the doc's "replay to recover" mechanism — it just bounds what gets replayed. Verified live: after replaying a ~75k-message backlog accumulated over this session's testing, killing and restarting `matching` resumed every market from its own recent snapshot offset (tens of thousands in), not from zero.
    - This same mechanism is also what makes Kafka's at-least-once redelivery safe (NFR-09, no double-execution) "for free" — since state is deterministically re-derived from the event log rather than trusted from a committed consumer offset, redelivering an already-processed message just recomputes the same result; nothing depends on offset-commit bookkeeping being exactly-once.
    - **Snapshot writes are async, off the matching hot path** — `SnapshotStore.Save` must return immediately; `snapshotstore.RedisStore` does this via a buffered channel + one background goroutine per store (not per market), and drops (logs, doesn't block) a snapshot if that queue is ever full rather than stalling the caller. Observed live under a large backlog-replay burst: the queue does fill up periodically ("스냅샷 큐가 가득 차서 이번 스냅샷은 건너뜀") — expected, self-healing backpressure, not a bug; a later snapshot for that market catches up once the burst subsides.
    - **`SnapshotStore.Handoff(ctx, Snapshot) error`** (FR-11) — a second, synchronous save path alongside `Save`. `Save`'s async/lossy queue is fine for occasional crash recovery, but is wrong for a *routine* market handoff (every rebalance, not just rare crashes): the lag between "last successfully async-saved offset" and "actual last-applied offset" would make the incoming instance's `Recover()` replay-and-republish already-published executions on essentially every handoff. `Engine.Handoff(ctx)` calls this directly, bypassing the queue — only called by `matching/kafkaclient` right after a market's per-partition goroutine has fully stopped reading (see below), never while `Apply` could still be running concurrently. `snapshotstore.RedisStore.Handoff` reuses the same `writeNow` primitive the async worker already used internally.
    - **`Engine.lastOffset`'s zero value is `-1`, not `0`** — found live while verifying FR-11 with two real instances: a market with zero orders ever (so `Apply` never ran) still got `Handoff`'d when its partition was reassigned, and if the zero-value int64 default (`0`) were used, the resulting snapshot would read `{"offset":0,...}` — indistinguishable from "offset 0 was actually processed." The next owner's `Recover()` would then resume from `snapshot.Offset+1 = 1`, permanently skipping whatever message eventually lands at the partition's real offset 0. `-1` means "nothing processed yet," so `Recover` correctly computes `resumeFrom = -1+1 = 0`. Regression test: `engine_test.go`'s `TestEngineHandoffWithNoEventsDoesNotSkipOffsetZero`.
  - **`kafkaclient/`** (`consumer.go`, `producer.go`) — `GroupConsumer` (`consumer.go`) replaces the old Phase-1-only `OrderReader`. It uses `kafka.ConsumerGroup` (with `matching/rebalance.LoadAwareBalancer` as its `GroupBalancer`) purely for group membership/leader-election/generation-fencing — actual message consumption never goes through the group's own commit/offset machinery. On each new generation, `Run` calls `gen.Start` once per assigned partition; each spawned goroutine (`consumePartition`) maps its partition index to a market name (same `TargetMarkets`-ordered scheme as `orderapi`'s `marketPartitioner`), calls the injected `MarketLifecycle.Acquire(market)` to get a fresh `Engine` and its `Recover`-derived resume offset, then subscribes directly via a **group-less** `kafka.Reader{Partition: N, GroupID: ""}` (`Partition` and `GroupID` are mutually exclusive in `segmentio/kafka-go`) seeked with `SetOffset(resumeFrom)` — Kafka's own committed-offset tracking is never trusted, exactly like Phase 1. When the generation ends (`ctx.Done()`, i.e. this partition is being reassigned), the goroutine stops reading and calls `MarketLifecycle.Release(market)` — which the real implementation (`matching/main.go`'s `marketRegistry`) wires to `Engine.Handoff` — *before* returning; `Generation.Start`'s documented guarantee ("the consumer group will wait for all functions launched by Start to exit before the group can move on") is exactly what makes this "old owner fully stops and confirms its state before the new owner's `Acquire` runs" ordering hold across process boundaries, without any hand-rolled lock. This hybrid (group for membership, direct `Reader` for reads) was validated beforehand with a disposable spike against real local Kafka: zero duplicate `(partition, offset)` processing across both a join-triggered and a force-kill-triggered rebalance, at the cost of a real, now-documented trade-off — the whole group briefly pauses (session-timeout-bounded on a hard kill, ~tens of seconds) during a rebalance. `ExecutionProducer` publishes to `executions` keyed by market via `&kafka.Hash{}` (this topic isn't consumer-group-partitioned by anything yet, so the 1-market=1-partition bijection doesn't matter here the way it does for `orders`) and `AllowAutoTopicCreation: true`. Both topics' message shapes are **provisional** (FR-22 doc doesn't exist yet, same situation as `orderapi`).
  - **`snapshotstore/`** (`redis.go`) — `RedisStore` implements `engine.SnapshotStore` (`Load`/`Save`/`Handoff`) against real Redis; the JSON shape it writes under key `orderbook:{market}` is independently re-declared (and must be kept in sync by hand) in `orderapi/orderbook.go`, which is the only other reader of that key.
  - **`rebalance/`** (`assign.go`, `loadtracker.go`, `balancer.go`) — pure-logic FR-11 package, no Kafka/Redis dependency in its core algorithm (fully unit-tested, same philosophy as `orderbook/`). `Assign(loads []Load, members []string) map[string]string` is LPT (Longest-Processing-Time-First) greedy: sort markets by load descending, repeatedly assign each to whichever member currently has the least total assigned load; ties break first by load-then-count (**not** load alone — see below) and finally by market name for full determinism, since `AssignGroups` only runs on whichever instance Kafka elects group leader, and a different leader on the next rebalance must compute the identical assignment from the identical input. **Found live, fixed**: the original tie-break compared `totals[m] < totals[least]` only — when all loads are equal (most commonly the all-zero cold-start case, before any throughput has been measured), `totals` never changes, so the comparison always resolved to the first member in sorted order and every market piled onto one instance instead of splitting evenly. Fixed by adding assignment-count as a secondary tie-break, so equal (including zero) loads now round-robin by count as intended. Regression test: `assign_test.go`'s `TestAssignZeroLoadSplitsEvenlyByCount`. `LoadTracker.Loads` measures each partition's recent throughput by diffing the broker's current `kafka.Conn.ReadLastOffset()` against a previous `{offset, timestamp}` reading persisted in Redis (keyed per market, survives leader changes) — no instance ever self-reports load, the broker is the sole source of truth. `LoadAwareBalancer` implements `kafka.GroupBalancer`, calling `Loads` + `Assign` inside `AssignGroups` and falling back to all-zero loads (i.e. even-by-count, thanks to the tie-break fix above) if the measurement call itself fails, so a transient Redis/Kafka hiccup during rebalance never stalls the whole group.
  - **`main.go`** — `marketRegistry` (implements `kafkaclient.MarketLifecycle`) owns `map[market]*engine.Engine` behind a mutex and is the sole place `Engine` instances get created: `Acquire` always builds a **brand-new** `Engine` and `Recover`s it from Redis rather than reusing any previous in-memory instance for that market (a market can be reacquired after being relinquished, and its last real state lives in Redis, not in a stale Go value) — this map guards *cross-market* concurrent access only; a single market's `Apply` calls still come from exactly one goroutine at a time, preserving `Engine`'s own no-internal-locking assumption. `consumerGroupID` is a fixed code constant (`"matching-engine"`, not an env var) shared by every instance in the deployment — same "fixed convention, not per-environment" rationale as `ORDERS_TOPIC`'s default.
  - **`orderapi`'s `order.Store` still never learns about fills** — `cancelOrderHandler`'s `ORDER_ALREADY_FILLED` 409 check (FR-03's own verification criterion) has no data source, since nothing consumes `executions` back into `orderapi`. Doesn't affect `matching`'s own correctness (a CANCEL for an order the book no longer has is just a no-op), but the API-level contract stays unfulfilled until something (future "기록기", or `orderapi` itself) wires status updates back. Determinism discipline remains a rule, not an automated guard beyond the one replay test: nothing in `orderbook`/`engine` may depend on `time.Now()` or Go map iteration order, since both `Recover` and `AssignGroups`' determinism depend on it.
  - Verified end-to-end against real local Kafka + Redis (`infra/dev-kafka`, `infra/dev-redis`) with the `orders` topic recreated at 20 partitions (one per market, a one-time local migration — a fresh deployment should just create it at 20 from the start): real `trader`/direct-`curl` traffic through `orderapi` into `orders`, `matching` consuming and producing correctly-shaped partial-fill executions to `executions` (confirming FR-07), `GET /v1/markets/{market}/orderbook` returning correctly-sorted, never-crossed bid/ask levels, and the FR-08/NFR-11 recovery behavior described above. **FR-11 specifically**, with 2 real instances: (1) a deliberately skewed load (one market flooded with 400 orders, three others with 5 each, the rest with zero) joined by a second instance correctly isolated the heavy market alone on one instance while the other 19 landed on the other — confirming volume-based, not count-based, splitting; (2) force-killing the instance holding the heavy market and waiting out Kafka's session timeout, the survivor picked up all 20 markets, with the heavy market resuming from its exact last-processed offset (no replay, no gap); (3) dumping the `executions` topic after both scenarios and comparing every `(buyOrderId, sellOrderId)` pair found zero duplicates (205 records, 205 distinct pairs) — no double-processing across either the graceful rebalance or the crash-handoff path.

- **`replayengine/`** — separate Go module (`module replayengine`, own `go.mod`), the replay engine (FR-18/19/27): reads `trader`'s FR-17 order-record files and resubmits them to `orderapi` (`POST /v1/orders`) with **no judgment logic** — same side/price/quantity, just re-paced by `ts` gaps like `trader/replay` does for market data. `requirements.md` 1.1.3/FR-18: "AI 트레이더는 실행마다 판단이 달라져... 모든 성능 측정은 [리플레이]를 기준으로 수행한다" — this is the fixed, reproducible-input counterpart to paper trading that actual before/after performance comparisons depend on.
  - **`orderstore/`** (`storage.go`, `local.go`, `s3.go`) — the **read-side** counterpart to `trader/orderstore` (which only ever writes). Independently re-declares `RecordedOrder` and the exact same `objectKey`/`formatFileTime` rules (`{market}/{YYYYMMDDTHHMMSSZ}_{YYYYMMDDTHHMMSSZ}_orders.json`) — these **must** stay byte-identical to `trader/orderstore/storage.go`'s or `replayengine` silently can't find the files `trader` wrote. `LocalFileStorage` (default, reads `./orders/` — same relative location `trader` writes to) and `S3Storage` (same bucket/region convention as `trader/orderstore/s3.go`; bucket doesn't exist yet, so only local is verified so far). `ErrNotFound` for a market with no recorded orders in that period is expected, not an error — plenty of markets have zero orders on any given replay day.
  - **`submitter.go`** — `HTTPOrderSubmitter`, deliberately built as a near-copy of `trader/order/http_submitter.go` (same `orderRequest` shape, fresh `Idempotency-Key` per call). `NewHTTPClient` applies the `MaxIdleConnsPerHost` fix from day one (see `trader/client/` above) since the same "many market goroutines share one client" shape applies here too.
    - **A second, more fundamental connection-reuse bug, found the same way**: even with a large idle-connection pool, replaying all 20 markets at high speed (`-speed=500`, ~1,450 req/sec aggregate) still produced a burst of `connectex: Only one usage of each socket address` failures right at the tail end where most markets finish near-simultaneously. Root cause turned out to be **not pool size at all** — `Submit` only called `io.ReadAll(resp.Body)` on the *error* path; on a successful 202 it never drained the body before `resp.Body.Close()`, and Go's `net/http` transport cannot return a connection to the idle pool unless its body was read to EOF first. Undrained-but-closed connections get torn down instead of reused, so the pool was constantly cycling brand-new connections regardless of its configured size — the actual fix was reading the body unconditionally (success or failure) before checking the status code. Re-verified after the fix: same `-speed=500` run against real recorded data, zero connection errors. **`trader/order/http_submitter.go` had the exact same latent bug** (same only-read-on-error pattern) — fixed there too as part of this finding, even though it hadn't visibly misbehaved yet at the lower speeds `trader` had been tested at.
  - **`replay.go`** — `replayMarket` is `trader/replay/replay.go`'s pacing loop (`gap := time.Duration(o.TS-lastTS)*time.Millisecond; wait := gap/speed`) minus all the bot/`MarketState` machinery — it just walks the recorded array in order and submits. `filterRange` implements FR-27's "구간 지정" at a basic level (`-from-ts`/`-to-ts`, Unix ms; a real "pick from a list of past replay sessions" UI/API doesn't exist since the frontend isn't wired to anything backend-side yet).
  - **`main.go`** — parses `-date`/`-speed`/`-order-bucket` (all same meaning as `trader`'s) plus `-shard-index`/`-shard-count` for FR-19. Market-level sharding (`i % shardCount == shardIndex` over `TargetMarkets`) needs **no coordination between instances at all**, unlike `matching`'s FR-11 — each market's record file is already an independent unit with zero shared state, so distributing markets across instances is just "which subset of files does this process attempt to load," decided independently by each instance from its own flags. This is why FR-19 didn't need a Phase 1/Phase 2 split the way `matching`'s FR-11 did.

    - **No `mode` field carried through the API.** `docs/api-specification.md`'s `POST /v1/orders` request body (`{market,side,price,quantity}`) has no way to mark "this order came from a replay, not paper trading" — but `erd.md`'s `TRADE_ORDER.mode` (`PAPER_TRADING`/`REPLAY`) and FR-18's "체결 결과는... DB에 저장한다"(구분해서) both assume that distinction survives downstream to whatever eventually writes to RDS ("기록기", not built yet). Today, a replayed order is indistinguishable from a live paper-trading order once it reaches `orderapi` — fixing this means changing role A's request contract (a new field or header), which is out of scope for a new standalone `replayengine` to decide unilaterally. Flagged here so it isn't silently lost before "기록기" gets built.

### Data flow

Upbit REST/websocket (`upbit` package) → Go structs (`Candle`, `TradeTick`, `UpbitTicker`) → **JSON files persisted to AWS S3** → served to the trader app on request. **Decided: this path does not use Kafka** — an earlier `backend/kafka/producer.go` wrapper was built to carry Upbit data onto a Kafka topic (per an earlier draft in `docs/requirements.md`), but market data here is historical/finite/already-`ts`-sorted and has exactly one consumer per request, none of which benefit from Kafka's pub-sub/backpressure/ordered-live-stream strengths — so it was deleted rather than left unused. (Kafka remains the right tool for the *separate* live order flow — `orders`/`executions` topics — which `orderapi/` and `matching/` now implement for real.)

The trader app is **pull-based and now exists** (`trader/`, see below): it does not receive data automatically at startup. It requests simulation data for a period from the backend, and the backend responds with the JSON file(s) covering that period (read from S3). See [docs/market-data-api.md](docs/market-data-api.md) for the full spec and sequence diagram; summary: `POST /v1/collect` triggers collection, `GET /v1/markets/data?date=...` returns a manifest of URLs for all 40 files (20 markets × batch/stream), the trader fetches them individually/in parallel via `GET /v1/markets/{market}/{batch|stream}` — backend proxies file bytes, no S3 presigned URLs, so the trader never needs S3 credentials — and per-market replay pacing (walking `events` by `ts` gaps) happens entirely client-side in memory, decoupled from the HTTP download.

**Decided and implemented**: the on-demand-generation trigger (hybrid design above) belongs to the per-file GET handler, not the manifest — the manifest stays cheap/fast (no existence checks, no `dataset.Storage` access at all) and `GET /v1/markets/{market}/{batch|stream}` (`fileHandler`) checks whether its file exists and triggers `collectMarket` for just that one market if not. Since `collectMarket` produces both batch and stream together in one call, concurrent batch+stream requests for the same market+date are deduped via `ensureMarketCollected`'s `singleflight.Group` (see `collector.go`) rather than running `collectMarket` twice — verified by firing concurrent batch/stream requests for an uncollected date and confirming the collection log line appeared exactly once.

### Output JSON file format (finalized design, not yet implemented)

Collected data is persisted as JSON, split into two files per requested period because the trader app consumes them differently:

- **Batch file** — day/week/month/year candles. Delivered as one lump snapshot; the trader app doesn't need it in time order.
- **Stream file** — second/minute candles + individual trade ticks, merged into a **single array sorted ascending by `ts`**. The trader app walks this array in order and paces its outgoing traffic by the gap between consecutive `ts` values, so all the merge/sort work happens at generation time, not in the trader app.

Field names are normalized across both files (see mapping table below) instead of reusing Upbit's raw field names, so the trader app has one consistent shape regardless of candle unit.

**Batch file**
```json
{
  "market": "KRW-BTC",
  "range": { "start": "2026-07-29T00:00:00+09:00", "end": "2026-07-30T00:00:00+09:00" },
  "candles": {
    "days":   [ { "ts": 1785283200000, "open": 0, "high": 0, "low": 0, "close": 0, "volume": 0 } ],
    "weeks":  [ ... ],
    "months": [ ... ],
    "years":  [ ... ]
  }
}
```

**Stream file**
```json
{
  "market": "KRW-BTC",
  "range": { "start": "2026-07-29T00:00:00+09:00", "end": "2026-07-30T00:00:00+09:00" },
  "events": [
    { "type": "trade_tick",    "ts": 1785283200123, "price": 0, "volume": 0, "side": "BUY" },
    { "type": "candle_second", "ts": 1785283201000, "open": 0, "high": 0, "low": 0, "close": 0, "volume": 0 },
    { "type": "candle_minute", "ts": 1785283260000, "open": 0, "high": 0, "low": 0, "close": 0, "volume": 0 }
  ]
}
```

**Field name mapping (Upbit raw → normalized JSON)** — kept explicit because `trade_price` means a different thing in each source struct: candle close vs. tick execution price.

Candle (all units — seconds/minutes/days/weeks/months/years):

| Upbit field | JSON field | Meaning |
|---|---|---|
| `timestamp` | `ts` | Candle time, UTC epoch ms |
| `opening_price` | `open` | Open |

Dev writes to local disk via `dataset.localStorage` instead; `APP_ENV` in `backend/config` selects between the two.

### Multi-market collection (implemented)

`upbit.TargetMarkets` (`backend/upbit/markets.go`) lists the ~20 target markets/coins; `collectAllMarkets` (`backend/collector.go`) loops over all of them for every request. Decisions so far:

- **One batch file + one stream file per market** (not one shared file for all markets) — keeps re-collection/re-generation of one coin from touching the others, and maps directly onto the S3 key layout below.
- On the trader-app side, the intended design is **one goroutine per market**, each independently walking its own stream file's `events` array in `ts` order and pacing sends by the gap between consecutive `ts` values — this is what actually produces the "many coins trading concurrently" load pattern, not just a speed optimization. Goroutines should share a single HTTP client / Kafka producer rather than each opening their own connection, and errors in one market's goroutine must not abort the others (isolate per-goroutine, collect via `WaitGroup`/`errgroup`).

### S3 storage design (decided so far, not yet implemented)

- **Key layout**: `s3://{bucket}/{market}/{start}_{end}_batch.json` and `.../{start}_{end}_stream.json` — period encoded in the filename, market as a path prefix.
- **Idempotency, not overwrite**: re-requesting the same market+period is not expected in normal use, but as a safety check, the backend should `HeadObject` before generating — if the file already exists, serve it as-is instead of regenerating/re-uploading.
- **No lifecycle policy**: this project's premise is re-running the *same* simulation dataset against evolving infra to measure improvement, and the project timeline is ~1 month, so objects must not expire or auto-transition to a cheaper storage class.
- **Access scope**: only the backend talks to the **market-data** bucket (`team1-truss-market-data`, IAM policy scoped to the backend) — the trader app never gets credentials for it, only the backend's request/response API. **This does not extend to order records (FR-17)** — see the "Order records" subsection right below; that's a deliberate, separate decision for a separate bucket.
- **Auth (dev vs. prod)**: final deployment target is AWS (EC2 or EKS), but local development also needs to work. The AWS SDK's default credential chain handles this without code branching — env vars/shared profile locally, IAM role automatically in AWS (EC2 instance profile, or **IRSA** for EKS — IRSA is a cluster/infra setup task: OIDC provider + IAM role trust policy + ServiceAccount annotation, not application code). The same env-var-driven pattern should extend to the planned dev-local-DB vs. prod-RDS split — connection target read from an env var (`.env` locally via the already-added `godotenv` dep, ConfigMap/Secret in EKS), not hardcoded or branched on environment in code.

### Order records (FR-17, implemented in `trader/`)

`requirements.md` FR-17: every order generated during paper trading must be recorded to a file, time-ordered, saved to S3 — that file becomes FR-18 (replay)'s input later. **Decided**: unlike market data, this goes to a **separate S3 bucket from `team1-truss-market-data`**, and **the trader writes to it directly** (not via the backend) — this is a deliberate exception to the "only backend talks to S3" rule above, made specifically for order records.

- **New bucket needed, not yet created**: proposed name `team1-truss-order-records` (same `team1-truss-*` convention as the market-data bucket), region `ap-northeast-2`. Whoever is doing infra work needs to provision it plus an IAM policy granting the trader `PutObject` (and eventually `GetObject`/`ListBucket` once FR-18/replay reads these back) — analogous to `infra/iam.tf`'s `team1_ec2_role`/`team1_ec2_s3_policy` but as its **own** role (e.g. `team1_trader_role`), not reusing backend's, so the two stay scoped independently.
- **Until the bucket exists**: `trader/main.go`'s `-order-bucket` flag defaults to empty, which selects `orderstore.NewLocalFileStorage("orders")` (writes to a local `orders/` dir) instead of `orderstore.NewS3Storage`. Pass `-order-bucket=team1-truss-order-records` once the bucket and IAM are ready — everything else (recording, flush timing, file shape) is identical either way, only `orderstore.Storage`'s implementation changes.
- **How recording happens**: `order.Order` gained a `TS int64` field (`time.Now().UnixMilli()`, set in `NewOrder`) — not part of the real order-acceptance API's request shape, only used for the record. `order.RecordingSubmitter` (`trader/order/record.go`) wraps any `OrderSubmitter` and records only orders whose underlying `Submit` succeeded — matching FR-17's verification criterion "기록 건수와 접수 건수 일치" (recorded count == accepted count). `order.InMemoryRecorder` buffers per-market in memory (mutex-protected, since multiple bot goroutines record concurrently) and **sorts by `TS` in `Snapshot`**, not at insert time — concurrent goroutines' `Record` calls can interleave slightly out of `TS` order under scheduling, the same reason `dataset.BuildStream` sorts its merged events rather than trusting insertion order.
  - **`InMemoryRecorder.mu` design — decided, revisit only if measured as a bottleneck**: up to ~62 goroutines (3 algorithmic bots × 20 markets + 2 global bots) can call `Record` concurrently on the *same* shared `InMemoryRecorder`, all serialized through one `sync.Mutex`. A lock-free alternative was discussed — give each producer goroutine its own local buffer (no shared state, no lock during the run) and k-way-merge them by `TS` at the end — which is a legitimate, commonly-used pattern for exactly this contention shape. **Decided to keep the current shared-mutex design for now**: a real end-to-end run (20 markets, up to ~118k recorded orders in one market) completed in ~1-2s with no observed slowdown, and the final sort step is needed either way (sorting one unsorted list vs. merging several pre-sorted ones — similar cost at this scale), so the extra plumbing (per-goroutine buffers + a merge routine) isn't earning its complexity yet. If lock contention is ever actually measured as a bottleneck (e.g. order volume scales up much further), switch `InMemoryRecorder` to the per-goroutine-buffer + merge design then, not preemptively.
- **`replay`/`bot` packages are untouched** — they only ever see the `OrderSubmitter` interface, so wrapping it in `RecordingSubmitter` is invisible to them. This is the same "decouple judgment from mechanics" pattern used throughout `trader/`.
- **Flush timing — end of the whole run, not per-market**: `main.go` only writes records out after *both* `wg.Wait()` (all markets' `ReplayMarket` goroutines done) *and* `globalWG.Wait()` (the global AI bots done). The global bots run until every market finishes, not just one — flushing a market's records as soon as its own `ReplayMarket` ends could miss orders the global bots place for that market afterward. Same reasoning as market-data collection producing one complete file rather than streaming incrementally.
- **File shape** (`trader/orderstore`, key layout `{market}/{start}_{end}_orders.json`, same convention as the market-data bucket):
  ```json
  { "market": "KRW-BTC", "range": { "start": "...", "end": "..." }, "orders": [ { "ts": 1785283200123, "side": "BUY", "price": "90000000", "quantity": "0.01" } ] }
  ```

### Upload/generation timing — hybrid (decided)

Simulation data is served via **both** pre-generated files and on-demand generation: some batch/stream files may be created ahead of time, but the trader app can also request a market+period that doesn't exist yet, triggering on-the-fly collection from Upbit → S3 upload → serve. The `HeadObject`-based idempotency check above is what makes this work either way. `POST /v1/collect` (see Architecture above) is the on-demand-collection trigger; it always runs across all 20 `upbit.TargetMarkets` for the requested date rather than accepting a single market — there's no per-market request shape yet. The trader-app-facing "give me the file(s) for this period" read/serve API is still not designed.

## Infra (Terraform)

`infra/` holds this project's Terraform. **This AWS account (`727646470302`, `ap-northeast-2`) is shared across multiple teams** — other teams' buckets/roles already exist there (`team5-*`, `team2-doro-*`, etc.), so anything created here is namespaced `team1-*` to avoid collisions.

- **`infra/bootstrap/`** — one-off bootstrap stack that creates the Terraform state bucket itself (chicken-and-egg: the state bucket can't be its own backend on first apply). Its own state now lives in that same bucket under `bootstrap/terraform.tfstate` (see below) — it was applied once with local state, and after the bucket existed, migrated onto S3 and the local `.tfstate` was removed. **Local Terraform state in this repo's working directory has already been lost once** (this folder appears to sync via OneDrive, which is suspected to have interfered with the local `.tfstate` file) — this is why bootstrap state was moved onto S3 immediately rather than left local.
- **`infra/`** (root) — main stack, backed by S3 remote state.

**S3 buckets (both created, both tagged `Team = team1`):**
- `team1-terraform-state-s3` — Terraform state. Versioning + SSE-S3 encryption + full public-access block. Holds two state files as separate keys in the same bucket:
  - `bootstrap/terraform.tfstate` — the bootstrap stack's own state (`infra/bootstrap/`)
  - `truss/terraform.tfstate` — the main stack's state (`infra/` root)
  
  Any future Terraform stack (e.g. for EC2/EKS compute) should follow the same convention: new `key = "<stack-name>/terraform.tfstate"` in this same bucket, rather than a new bucket.
- `team1-truss-market-data` — the batch/stream JSON data bucket described above. SSE-S3 encryption + full public-access block, **no lifecycle rules** (per the "no lifecycle policy" decision above).

**Both bucket resources have `lifecycle { prevent_destroy = true }`** in their Terraform config — an accidental `terraform destroy` or a config change that would force-replace the bucket will error out instead of deleting it. **Decided**: the backend authenticates to `team1-truss-market-data` via whatever EC2 instance profile / EKS IRSA role ends up running it — not via a separate personal/dev IAM user. `infra/iam.tf` already provisions `aws_iam_role.team1_ec2_role` / `aws_iam_role_policy.team1_ec2_s3_policy` (scoped to just this bucket) / `aws_iam_instance_profile.team1_ec2_profile`, kept around specifically so the next compute (EC2 or EKS) can attach it without recreating it. This was verified once already: a temporary EC2 in `infra/network.tf`'s public subnet ran the backend with this instance profile and uploaded all 20 markets to S3 successfully, then was torn down (the EC2 instance, its keypair, and its security group — not the IAM role/policy/instance profile, which stay). Terraform itself authenticates as the shared student IAM user (`a-student-05`), which already has broad account permissions — that's fine for provisioning resources but is not the identity the backend uses at runtime.

## Conventions

- Comments and log/print messages in this codebase are written in Korean; match that style when editing existing files in `backend/upbit`, `backend/dataset`, and `orderapi/`.
- **Inter-app connection config (URLs, and later DB/cache endpoints+credentials) is always env vars via `.env`/`godotenv`; CLI flags are only for per-run simulation parameters — decided, revised from an earlier CLI-flag-based design.** `trader` originally took `-backend`/`-orderapi` as flags, but that doesn't scale once secrets enter the picture: an RDS/Redis endpoint is fine either way, but a password passed as a CLI flag shows up in `ps`/shell history on shared systems, so it can't go there — and splitting "URLs as flags, passwords as env vars" would just be two config systems to remember. So all three modules now load connection config the same way: `backend/config.go`'s `Load()`, `orderapi/config.go`'s `LoadConfig()`, and `trader/config.go`'s `LoadConfig()` each read `.env` via `godotenv` (missing `.env` is logged, not fatal — expected in prod where real env vars are injected directly).

  **Required (`log.Fatal` if unset) vs. default-and-continue — decided.** A var that legitimately differs per environment, where a wrong silent value fails *later and confusingly* instead of *immediately and clearly*, must be required: `backend`'s `S3_BUCKET` (prod only — wrong value means data silently goes to local disk instead of S3), `orderapi`'s `KAFKA_BROKER`, `trader`'s `BACKEND_URL`/`ORDERAPI_URL` — all of these defaulting to `localhost` outside local dev would mean the process starts "successfully" and only fails once it actually tries to connect, deep inside a library, instead of at startup with a clear message. A var that's effectively the same across environments and fails obviously if wrong keeps a default: `PORT` (everywhere — a wrong bind port just fails the health check immediately) and `orderapi`'s `ORDERS_TOPIC` (the topic name is a fixed convention per the docs, not something that varies by deployment). `backend`'s `APP_ENV` is unconditionally required (no valid default exists for "which environment am I"). Each module's local `.env` (gitignored, one per module: `backend/.env`, `orderapi/.env`, `trader/.env`) supplies the required vars for local dev — there is no hardcoded `localhost` fallback to lean on anymore.

  `trader/main.go`'s `-date`/`-speed`/`-order-bucket` stay CLI flags — these are simulation run parameters you genuinely want to vary per invocation (e.g. looping over dates in a shell script), not connection targets, so the flag/env-var split tracks "what changes per run" vs. "what the service connects to", not module boundaries.
- **Date boundaries are KST (UTC+9), not UTC — decided.** Every `date=YYYY-MM-DD` the API accepts (`POST /v1/collect`, `GET /v1/markets/data`, `GET /v1/markets/{market}/{kind}`) means that KST calendar day, not the UTC one — a request for `2026-07-27` collects `2026-07-27T00:00:00+09:00` through the instant before `2026-07-28T00:00:00+09:00`. Upbit is a Korean exchange, and the team decided this reads more naturally than UTC-shifted-by-9-hours days. `upbit.KST` (`backend/upbit/ticks.go`) is the shared `*time.Location`, built via `time.FixedZone("KST", 9*60*60)` rather than `time.LoadLocation("Asia/Seoul")` — Korea has no DST so the fixed offset is always correct, and `FixedZone` has no dependency on the OS/container having the IANA tzdata database installed (`LoadLocation` would fail on minimal images like Alpine without the `tzdata` package). `backend/server.go`'s `parseDate` helper is the one place all three handlers parse the incoming date string, via `time.ParseInLocation(..., upbit.KST)`.
  - **Two traps this hit while switching from UTC, worth knowing about**: (1) `upbit.FetchTradeTicksForDate` used to hardcode `time.UTC` when reconstructing its day boundary from `date.Year()/Month()/Day()` — discarding whatever `Location` the caller actually passed in. Fixed by using `date.Location()` instead of a hardcoded zone, so the function works correctly regardless of which zone callers use. (2) Its `daysAgo` calculation used `time.Now().UTC().Truncate(24 * time.Hour)` to find "today's start" — **`time.Time.Truncate` ignores `Location` entirely** (it rounds down against the absolute time since Go's zero time, which is UTC-aligned), so swapping in `.In(kst)` before `Truncate` would silently keep truncating to UTC midnight, not KST midnight. Fixed by reconstructing "today" the same way as `startOfDay` — `time.Date(now.Year(), now.Month(), now.Day(), 0, 0, 0, 0, loc)` — never `Truncate` for a timezone-aware day boundary.
  - `dataset`'s `formatFileTime` (file/S3 key timestamps, `local_storage.go`) and `toRange` (the JSON `range.start`/`range.end` fields, `build.go`) both display in KST too, for the same reason as the date boundaries — a file for `2026-07-27` should visibly read `20260727...`, not a UTC-shifted `20260726T150000...`. `formatFileTime`'s layout dropped the trailing `Z` (that specifically denotes UTC in ISO 8601 and would be wrong now); `toRange` still uses `time.RFC3339`, which renders the `+09:00` offset instead of `Z` — still fully valid, unambiguous RFC3339.
  - `upbit/candles.go`'s `FetchCandlesInRange`/`FetchRecentCandles` needed **no changes** — they only ever compare absolute `time.Time` instants (cursor-based pagination), never reconstruct a calendar day from `Year()/Month()/Day()`, so they're correct regardless of which `Location` the `start`/`end` they're given came from. `trader/` also needed no changes — it only ever passes the `date` string through to the backend as-is.
  - Verified end-to-end against real Upbit data: requesting `date=2026-08-02` produced a stream whose first event's `ts` converts to exactly `2026-08-02T00:00:00+09:00` and last event's `ts` to `2026-08-02T23:59:59+09:00`.
